## 1. Resolver definitivamente a custódia DPAPI

### Arquivos principais

- `tools/quality/ap06_key_custody.py`
- `tools/quality/ap06_r11_keys.py`
- `tools/quality/ap06_authorities.py`
- `tools/quality/run_ap06_r12_r2.py`
- Rotinas existentes que geram `runtime-credentials.dpapi`, `runtime-credentials-custody.json` e seus readbacks.

### Problema concreto

Em `verify_preflight_dependencies()`:

```python
custody = read(
    wave.output / 'baseline/runtime-credentials-custody.json'
)

require(
    custody.get('protectedSha256') ==
    sha256(wave.output / 'baseline/runtime-credentials.dpapi'),
    'R12R8_PREFLIGHT_NOT_READY'
)
```

Na R12-R8, o hash não correspondeu.

Há também uma diferença importante de origem: `ap06_r11_keys.py` lê a autoridade privada `keys/fdks.dpapi`, enquanto o gate valida um blob local `baseline/runtime-credentials.dpapi`.

**Primeira obrigação: localizar os produtores de ambos os arquivos e determinar se representam cópias idênticas, selagens distintas do mesmo material ou credenciais de finalidades diferentes. Não presumir equivalência sem examinar os contratos.**

### Diagnóstico somente de leitura

Antes de modificar qualquer arquivo:

1. Localizar a função que cria cada blob e seu recibo.
2. Verificar identidade, origem, manifesto e escopo DPAPI.
3. Comparar SHA-256/tamanho dos arquivos existentes com os recibos das autoridades privadas.
4. Validar ownership, ACL e ausência de reparse points.
5. Executar readback independente e unseal somente em memória.
6. Identificar se a divergência surgiu de cópia, re-selagem, reutilização indevida ou recibo incorreto.

DPAPI pode produzir ciphertexts diferentes em proteções independentes do mesmo plaintext. Portanto, **hash diferente entre dois blobs legitimamente re-selados não prova divergência de credenciais**. Entretanto, hash diferente do recibo que afirma identificar aquele arquivo é uma falha de integridade e deve ser rejeitado.

### Correção obrigatória

Preferir uma única fonte de verdade para cada artefato:

- Se o runtime deve conter uma cópia da autoridade original, copiar os bytes já protegidos e validar hash/size contra a origem imutável.
- Se o runtime precisa de uma selagem independente, gerar uma nova custódia **antes da tentativa R12-R9**, registrar sua proveniência e comparar o conteúdo semântico de forma segura em memória quando essa equivalência fizer parte do contrato.
- Se os artefatos tiverem finalidades diferentes, validar cada um contra seu próprio recibo, preservando o vínculo entre autoridades e campanha.

Nunca simplesmente executar:

```python
custody['protectedSha256'] = sha256(current_blob)
```

para aceitar um blob antigo sem origem comprovada.

Nunca modificar o recibo R12-R8.

Implementar um validador pequeno e reutilizável, por exemplo:

```python
def verify_runtime_key_custody(
    blob_path, receipt, manifest_sha, identity
):
    require(
        receipt['manifestSha256'] == manifest_sha,
        'R12R9_DPAPI_MANIFEST_MISMATCH'
    )
    require(
        receipt['identity'] == identity,
        'R12R9_DPAPI_IDENTITY_MISMATCH'
    )
    require(
        sha256(blob_path) == receipt['protectedSha256'],
        'R12R9_DPAPI_CUSTODY_MISMATCH'
    )

    # Validar CurrentUser, entropy e readback
    # contra o contexto autorizado.
    # Não imprimir nem persistir plaintext.
```

Adaptar ao schema real; não inventar campos ou alterar contextos DPAPI históricos.

Quando a equivalência de plaintext for exigida entre duas selagens válidas, usar comparação em memória de conteúdo autenticado, sem criar hash público do material secreto e sem gravar chaves temporárias.

Preservar `DPAPI CurrentUser`, SID, entropy, custódia dos três FDKs sintéticos e readback independente.

**Resultado obrigatório:** uma cadeia verificável entre autoridade, corpus, identidade, blob protegido, recibo e runtime, sem divergências ignoradas.
