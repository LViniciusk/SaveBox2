## 3. Implementar um freeze dry-run verdadeiro, antes do Chromium

Esta é a principal melhoria arquitetural desta TASK.

Hoje, boa parte das falhas do freeze só aparece após a execução do preflight.

Criar um **validador offline de prontidão do freeze**, que examine os mesmos inputs e contratos usados pelo freeze real, sem publicar snapshots científicos falsos.

### Implementação proposta

Extrair do `freeze_implementation()` a lógica de construção do conjunto de arquivos:

```python
def collect_freeze_inputs(wave, config):
    """Returns validated source paths and required authorities."""
    ...
    return files, publications
```

Depois utilizar o mesmo coletor nos dois fluxos:

```python
def validate_freeze_readiness(wave, config):
    files, publications = collect_freeze_inputs(
        wave, config
    )

    verify_source_files(files)
    verify_publication_dependencies(publications)
    verify_freeze_destination(wave)

    return {
        'status': 'PASS',
        'inputCount': len(files),
        'sourceManifestSha256': manifest_digest(files),
    }
```

O `freeze_implementation()` deve consumir esse mesmo plano validado.

Não manter dois coletores diferentes que possam divergir.

### Arquivos gerados pelo preflight

`angular-unit-1.json`, `preflight-ready.json` e `development-reservation.json` só existirão depois do navegador.

Separar:

- **Inputs estáticos:** exigidos e validados antes de qualquer Chromium.
- **Inputs dinâmicos:** existência, schema e relação de hashes validados com fixtures sintéticas offline; na execução real, verificar os artefatos efetivamente produzidos.

Uma simulação não pode passar como prova de que a medição real ocorreu.

Executar também um dry-run pós-preflight, sem consumir outro navegador, imediatamente antes de efetuar a publicação real.

### Publicação e readback

Validar previamente:

Para testar publicação, usar uma autoridade **descartável e isolada**, com dados sintéticos e o mesmo publisher real. Verificar publicação e readback independentes, depois limpar apenas essa autoridade de teste.

## 4. Fazer o freeze informar exatamente onde falhou

O runner atualmente converte exceções desconhecidas em:

`R12R2_EXECUTION_FAILED`

Essa categoria é insuficiente para diagnosticar um STOP após o preflight.

Para a R12-R11, implementar estágios específicos:

| Estágio | Classe |
|---|---|
| Input collection | `R12R11_FREEZE_INPUTS_INVALID` |
| Native build authority | `R12R11_FREEZE_NATIVE_AUTHORITY_INVALID` |
| Preflight receipt | `R12R11_FREEZE_PREFLIGHT_INVALID` |
| Corpus/credentials | `R12R11_FREEZE_CUSTODY_INVALID` |
| Snapshot publication | `R12R11_FREEZE_PUBLICATION_FAILED` |
| Publication readback | `R12R11_FREEZE_READBACK_FAILED` |
| Final hash/freeze | `R12R11_FREEZE_INTEGRITY_FAILED` |

Usar um contexto ou wrapper pequeno em vez de repetir `try/except` em todas as funções.

Exemplo:

```python
@contextmanager
def freeze_stage(stage):
    try:
        yield
    except EXPECTED_FAILURES as error:
        raise FreezeFailure(
            stage=stage,
            failure_class=FREEZE_ERRORS[stage]
        ) from None
```

Preservar o erro original apenas nos logs privados controlados, quando seguro. O recibo público deve conter estágio e código sanitizados, nunca caminhos privados, credenciais ou stack traces.

Se uma publicação falhar após criar artefatos parciais, **não classificá-la como FROZEN** e não reutilizar ou sobrescrever aquela tentativa.

Não alterar os STOPs históricos.
