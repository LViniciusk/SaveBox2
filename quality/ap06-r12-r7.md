# TASK — AP-06 R12-R7: Browser Attestation State Machine Recovery + Factorial Execution

## Contexto e objetivo

**Repositório:** `LViniciusk/SaveBox2`<br>
**Branch:** `investigation/ap06-r12-r7`<br>
**Base:** `investigation/ap06-r12-r6` — PR #33<br>
**HEAD de referência:** `38df0ba8889da1bd087c7c80b2e8ae0833242217`<br>
**Entrega:** PR Draft empilhado sobre #33, sem merge.

A R12-R6 terminou em `R12R6_STOP` após consumir um Chromium no preflight. Os cinco casos funcionais passaram, mas a revalidação OS pós-workload falhou, seguida de falha no cleanup da attestation.

**Causa identificada:** `tools/quality/ap06_browser_identity.py` exige `previous is None` em toda chamada `attest`, apesar de `finishBrowserIdentity()` solicitar uma segunda attestation usando a mesma sessão.

O helper rejeita a segunda solicitação, encerra e impede que o cleanup comunique `audit-closed`/`release` corretamente.

**Objetivo:** corrigir a máquina de estados da attestation, preservar o helper durante cleanup, comprovar o protocolo completo sem Chromium científico e executar o fatorial sob nova autoridade R12-R7.

Não alterar produção, transporte, criptografia, corpus ou metodologia científica.

## 1. Corrigir a máquina de estados da attestation

### Arquivo principal

`tools/quality/ap06_browser_identity.py`

Código problemático em `main()`:

```python
require(
    action == 'attest' and previous is None,
    'AP06_BROWSER_IDENTITY_UNPROVEN'
)
```

A R12-R4 já suportava a segunda validação:

```python
result = validate_process(
    identity, observed, pid, parent_pid,
    required_args, previous,
    parent, node_executable, launch_started_ms
)

previous = previous or result
```

Restaurar esse comportamento, mas com estados explícitos para impedir attestações extras ou operações fora de ordem.

### Máquina de estados proposta

Estados mínimos:

- `READY`: lease aberto, nenhuma attestation.
- `BEFORE_ATTESTED`: primeira identidade validada.
- `AFTER_ATTESTED`: mesma identidade revalidada após workload.
- `AUDITED`: encerramento auditado.
- `RELEASED`: handles e lease liberados.
- `FAILED`: falha permanente da tentativa; apenas cleanup permitido.

Fluxo esperado:

```text
READY
  → attest
BEFORE_ATTESTED
  → register-processes (0..N)
  → attest
AFTER_ATTESTED
  → register-processes (0..N)
  → audit-closed
AUDITED
  → release
RELEASED
```

Implementação sugerida:

```python
if action == 'attest':
    require(
        state in ('READY', 'BEFORE_ATTESTED'),
        'AP06_BROWSER_ATTESTATION_ORDER_INVALID'
    )

    first = state == 'READY'

    result = validate_process(
        identity,
        observed,
        request['pid'],
        request['parentPid'],
        request['requiredArgs'],
        previous=None if first else initial_identity,
        parent=parent,
        node_executable=request['nodeExecutable'],
        launch_started_ms=request['launchStartedMs'],
    )

    if first:
        initial_identity = result
        state = 'BEFORE_ATTESTED'
    else:
        state = 'AFTER_ATTESTED'

    print(json.dumps(result), flush=True)
```

Adaptar aos contratos reais, mantendo o código enxuto.

### Regras obrigatórias

A segunda attestation deve:

- Reutilizar o mesmo browser PID.
- Conferir creation time original.
- Validar novamente executável, hash, arquitetura e versão.
- Conferir parent PID e creation time.
- Revalidar argumentos OS, profile e flags congeladas.
- Rejeitar troca de processo ou PID reutilizado.
- Retornar `identityBeforeWorkload=False`.

A primeira deve continuar retornando `identityBeforeWorkload=True`.

O terceiro `attest` deve falhar.

Não recriar o lease nem reiniciar o Chromium para realizar a segunda validação.

Preservar `validate_process()` e `OwnedProcessAudit`, evitando duplicar validadores.

## 2. Preservar o helper e a causa original durante falhas

Atualmente, uma exceção dentro do loop de `main()` encerra o processo Python. Isso pode impedir a auditoria dos handles mesmo quando o Chromium já foi iniciado.

Separar falhas do protocolo da finalização do helper.

Uma falha de attestation deve:

1. Gerar resposta `STOP` sanitizada.
2. Marcar a sessão como `FAILED`.
3. Impedir novas attestações e registros científicos.
4. **Manter disponíveis `audit-closed` e `release` para o cleanup**.
5. Finalizar o helper somente após release ou término forçado controlado.

Exemplo conceitual:

```python
try:
    result = handle_request(request)
except EXPECTED_ERRORS as error:
    failure = sanitize_failure(error)
    state = 'FAILED'
    print(json.dumps({
        'status': 'STOP',
        'reason': failure,
    }), flush=True)
```

A estrutura acima deve estar dentro do loop de mensagens. `audit-closed` e `release` precisam continuar aceitos no estado `FAILED`, quando houver recursos sob custódia.

Não permitir retries científicos após o STOP.
